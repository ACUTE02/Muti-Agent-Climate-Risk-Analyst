# Setup from a clean clone

Clone → working local API. One command does it; this document explains what that
command does and why the repository does not simply ship the files.

```bash
git clone <this repo>
cd Muti-Agent-Climate-Risk-Analyst

py -3.11 -m venv .venv
.venv\Scripts\activate                 # Windows;  source .venv/bin/activate on Linux/macOS
python -m pip install --upgrade pip
pip install -r requirements-phase1.txt -r requirements-phase2.txt \
            -r requirements-phase3.txt -r requirements-phase6.txt

echo GEMINI_API_KEY=your-key-here > .env

python -m scripts.setup                # regenerates everything, ~2-5 min
uvicorn api.app:app --reload --port 8000
```

Then open <http://localhost:8000/docs>, or check
<http://localhost:8000/health>.

## "The database disappears when I re-download the project"

This is expected, and it is not a bug — but it was previously undocumented and
unautomated, which is what made it feel like one.

**Every artifact the running system loads is derived data, and derived data is
git-ignored.** The repository tracks *source and evidence*: code, the corpus
manifest, the measured result files, `EVALUATION.md`. It does not track the
fetched weather series, the fitted models, or the ChromaDB index, because those
are outputs — regenerating them is cheap and committing them would put hundreds
of megabytes of reproducible binaries in git history.

What a fresh clone legitimately does not have:

| Missing after clone | Regenerated by | Needs network | Needs API key |
|---|---|---|---|
| `data/raw/*.parquet` — Open-Meteo weather | step 1 | yes | no |
| `models/oni_series.parquet` — NOAA ENSO index | step 2 | yes | no |
| `models/scaler_*.joblib`, `models/spi_params_*.joblib` | step 3 | no | no |
| `models/ridge_t1_*.joblib` | step 4 | no | no |
| `models/ridge_t2_*.joblib`, `ridge_t3_*.joblib` | step 5 | no | no |
| `retrieval/chroma_store/` — the vector index | step 6 | yes | **yes** |

`models/horizon_manifest.json` **is** tracked — it is the record of which model
answers which horizon and at what measured confidence, so it belongs with the
evidence rather than with the binaries.

### The part that was not obvious

`forecast_drought_risk()` loads `scaler_<region>.joblib` and
`spi_params_<region>.joblib` at request time. **Neither `forecasting.t1_model`
nor `forecasting.recursive` writes them** — both call
`prepare_dataset(..., save=False)`. The only modules that persist them are
`forecasting.train` and `forecasting.evaluate`: the *LSTM* path.

So the obvious-looking sequence — fetch, train the t+1 model, train the
horizons — produces a manifest, produces Ridge models that load fine, and then
dies on a missing scaler the first time anyone asks a drought question. On the
development machine those files existed only as a leftover side effect of Phase-1
LSTM training, for a model that has no skill and no longer serves any forecast.

`scripts/setup.py` step 3 persists exactly those artifacts by calling the
project's own `prepare_dataset(region, save=True)`, so setting up does not
require training a model nobody uses. **Verified byte-identical**: deleting the
four files and re-running step 3 reproduces the same SHA-256 for each, so a fresh
clone gets the artifacts every phase actually measured with, not merely
equivalent ones.

### Is the ChromaDB index portable?

Yes. Paths are computed at import time from `__file__`
(`retrieval/config.py`: `REPO_ROOT / "retrieval" / "chroma_store"`), and the
persisted store itself was scanned for baked-in absolute paths — **zero hits**.
A store built at `E:\...` works after cloning to any other drive or directory.
It is git-ignored because it is regenerable and large, not because it is fragile.

## The setup command

```bash
python -m scripts.setup              # full run; skips anything already present
python -m scripts.setup --check      # report what is missing, change nothing
python -m scripts.setup --skip-index # everything except the ChromaDB build
python -m scripts.setup --force      # re-run every step from scratch
```

Steps are idempotent: an existing output is skipped unless `--force`. Step 6
needs an API key and spends **embedding** quota — a separate budget from the
20/day `generate_content` cap — and backs off on 429, resuming from disk if
interrupted. Without a key, the step is skipped with a message and the API still
starts; retrieval questions will fail until it is built.

`--check` verifies exactly what `GET /health` verifies, so the two can never
disagree about whether the system is ready.

## Quota — read before clicking around

The Gemini free tier this project targets allows **20 `generate_content`
requests per day at 5 per minute** (measured, Phase 3.1 — not the 1,500/day the
project originally assumed).

One `POST /report` costs **2 calls** typically (routing + synthesis), a third if
synthesis needs its regeneration, and a fourth if the request routes to
`assess_crop_impact`. So a day's budget is roughly **5–8 reports**.

`GET /quota` reports what has been used, tallied at the single chat chokepoint
rather than estimated. When the quota runs out, `/report` returns **429 with a
specific explanation**, not a generic 500.

`/health`, `/quota`, `/examples` and `/evaluation` make **no** LLM calls and are
free to hit as often as you like.

## Running without an API key

Everything that does not talk to Gemini still works:

```bash
python -m scripts.setup --skip-index
pytest tests/ -v                       # 277+ tests, all offline by default
python -m crop_impact.tool rajasthan wheat 2006-02
python -m evaluation.checker_eval
uvicorn api.app:app --port 8000        # /health, /quota, /examples, /evaluation
```

Only `/report` and the retrieval index build need a key.

## Docker

```bash
docker build -t climate-risk-analyst .
docker run --rm -p 8000:8000 -e GEMINI_API_KEY=your-key-here climate-risk-analyst
```

The image bakes the ChromaDB index in at **build** time, per the project's
standing architecture decision that no zero-cost host offers persistent disk. The
API key is supplied at **run** time and is never baked into the image — the build
needs its own key passed as a build argument to embed the corpus.

No deployment-platform configuration is included. Where this gets deployed, if
anywhere, is a later decision.
